# Changelog

All notable changes, grouped by milestone. Updated at the end of each milestone.

## Milestone 1: Foundation (in progress)

### Added

- Design documents, screen specs and diagrams in `docs/design/`.
- Phase A understanding (`docs/UNDERSTANDING.md`) and open decisions (`docs/decisions/OPEN.md`).
- Milestone 1 plan and ADR-0001 (tenancy and RLS), ADR-0002 (auth and sessions), ADR-0003 (frontend architecture), all approved 2026-10-01.
- Repository skeleton: `.gitignore`, `.gitattributes`, `README.md`.
- Backend skeleton (T01b): Python 3.12, Django 5.2.17 LTS, settings split into base, local, test and production (driven by django-environ, refusing SQLite and unsafe production values), pinned requirements, ruff, mypy and pytest configuration, `.env.example`, and the twelve empty apps.
- Database roles (T02a): `dial_owner`, `dial_app` (NOBYPASSRLS) and `dial_platform` (BYPASSRLS) with per-database grants, a setup and verification script, migration scripts that run only as the owner, and `docs/ops/neon-dev.md`. Verified on the Neon `dev` branch.
- Test database harness (T02b): pytest creates and migrates the test database as `dial_owner`, applies the grants, then runs every test as `dial_app` over Neon's direct host. Tests prove the test role can't bypass RLS or create tables.
- Core (T03a): `BaseModel` (random UUID key, UTC timestamps); request IDs on every request, response (`X-Request-ID`) and log line; JSON logging that masks Kenyan phone numbers and redacts passwords, PINs, codes, tokens and secrets at any depth.
- API conventions (T03b): the error envelope `{code, message, fields, request_id}` for every error (DRF, Django 404/500), with user-safe messages and `retry_after` on 429; every error response rolls back the request transaction; cursor pagination (20 per page); `GET /api/v1/health` (database and Redis); the OpenAPI schema at `/api/schema/`, committed as `backend/openapi.yaml` and checked by `manage.py check_openapi`; `Accept-Language` support.
- Tenant context and layer 1 isolation (T04a): `tenant_context()` (contextvar plus transaction-local `app.business_id`, cleared even inside outer transactions), `TenantModel` with a manager that refuses to run without a business and a save/bulk-create guard, `unscoped` manager checked by a code-rule test; global `Business` and `BusinessDomain` with W-03 address rules and database constraints; a test-only tenant app.
- Row-level security and the tenancy contract (T04b): `EnableTenantRLS` (enable and force RLS plus the `tenant_isolation` policy, using `NULLIF` so an unset business always means zero rows) and `MakeAppendOnly` (revoke UPDATE and DELETE) migration operations; `BusinessBranding` (WCAG AA check on the primary colour) and `BusinessSetting` (typed registry, no M1 keys) with RLS; the global-model registry and `tests/test_tenancy_contract.py`; the test harness now sets default privileges before migrating, and the grant script no longer re-grants on existing tables.
- Host resolution and the per-request transaction (T04c): the business comes from the `Host` header through `BusinessDomain` (port and case ignored, cached 60 s, unknown hosts cached too); unknown hosts get a 404 envelope before any view; `/api/v1/health` is the only exempt path; the platform-admin host is served only by the platform-admin service; each business request runs in `tenant_context()`, and a 5xx response rolls it back; a code-rule test forbids session-level settings.
- Isolation proof and the cross-business harness (T04d): raw-SQL tests over every tenant table (seeded through per-model factories) prove business A never sees, changes or deletes business B's rows and that no business means no rows; `assert_cross_business_404` with `business_a`, `business_b` and `api_client_for` fixtures, which first requests as the owner and catches leaks RLS can't stop (such as caches keyed without the business); a meta-test requires it in every `apps/*/tests/test_api_*.py`.
- Users, phone numbers and minimal branches (T05a): `accounts.User` (per-business accounts; platform staff with no business, invisible to `dial_app`; fixed roles; status; personal PIN fields; the three staff rights), `BusinessPhoneBackend` signing in within the current business only, the X-13 password rules, one Kenyan phone module (`07…`, `01…`, `7…`, `1…`, `+254…`, `254…` to E.164; display and masked formats), and `Branch` and `BranchMember`. Django's auth app is installed; admin waits for T12.
- Audit log and outbox (T07a): append-only `AuditLog` (the database refuses edits and deletes; platform rows have no business) written by `audit.record()` with secrets redacted; `OutboxEvent` written in the same transaction by `outbox.emit()` and dispatched after commit to registered handlers, each in a savepoint, retried with backoff (30 s doubling to an hour, 10 attempts); `@tenant_task`; a per-business sweeper every minute (Celery beat); a code rule that tasks run inside a business. Fixed: `tenant_context()` now opens a fresh transaction when re-entered after its transaction ended (on-commit callbacks).
- Notifications (T07b): `send_sms()` writes a `Notification` and an outbox event in the caller's transaction; the worker renders and sends after commit. Catalogue texts (phone code, invitation) are the defaults, word for word; a business can have its own template per language; Swahili falls back to English. Failures retry 3 times, 5 minutes apart, then the message is marked failed and never raises. Codes and links are removed from what's stored once sent. Console backend for development, in-memory backend for tests; a code rule keeps backends behind the outbox.
- Sign-in sessions (T05b): `POST /auth/login` (X-10; the same message for any wrong phone or password; suspension revealed only after a correct password, naming the business's support contact), `POST /auth/refresh` (rotating httpOnly, Secure, SameSite=Strict cookie scoped to `/api/v1/auth`; reusing an old refresh token signs the session out), `POST /auth/logout`, `GET /me`, `GET /me/branches`. Access tokens (15 minutes) are bound to the business and the session, so a token never works on another business's address and sign-out takes effect at once. Throttles keyed by business plus user, IP or phone, with rates like `10/15m`. All endpoints are signed-in by default.
- SMS codes and passwords (T05c): `PhoneOTP` (6 digits, keyed hash, 10 minutes, 5 tries, a new code cancels the old, 3 sends an hour and 60 seconds apart per business; unknown numbers get the same answer and count towards limits but receive nothing); `POST /auth/password-reset/request`, `/verify` (attempts left on errors; returns a single-use 10-minute reset token), `/confirm` (validated before the token is spent; signs out everywhere and signs in) and `POST /auth/password/change` (signs out the other sessions). Apps earlier than notifications send SMS with `core.messaging.request_sms()` through the outbox; a code rule enforces the app dependency order.
- Invitations and the first PIN (T05d): `Invitation` (hashed link token, 7 days, one open invitation per phone), `InvitationBranch` and append-only `ConsentRecord`; `GET/POST /console/invitations` and `/resend`, `/cancel` (owners and managers; managers, accountants and staff only; managers only into their own branches; a number with an account is refused; inviting again updates and resends); the X-14 flow `GET /auth/invitations/{token}`, `/send-code`, `/verify`, `POST /auth/invitations/accept` (creates the verified account with rights and branch memberships, signs in); `POST /me/pin` (first PIN, 4 digits, common PINs refused, owners/managers/staff only). Invitation SMS uses the catalogue text with role labels; links follow `APP_LINK_SCHEME`/`APP_LINK_PORT`.
- Registered devices (T06a): `Device` (branch, hashed token, status, wrong-PIN count) and sessions linked to the device they run on; `POST /staff/devices` (S-02: owners for any branch, managers for their own; sets the httpOnly `das_device` cookie and signs the registering person out of the device); `GET /devices/current` (X-15: device, branch, lock state and the roster of active owners, managers and staff of that branch who have a PIN, by first name and surname initial).
- PIN switching and A-42 control (T06b): `POST /auth/pin-switch` (X-15: the device cookie plus a person on its roster and their PIN; ends the previous PIN session on the device; wrong PINs, including unknown people, count down and the fifth locks the device); signing in with a password on a registered device links the session to it, and a manager of that branch or an owner unlocks a locked device (D-37); `GET /console/sessions`, `POST /console/sessions/{id}/sign-out`, `GET /console/devices`, `POST /console/devices/{id}/remove` (ends every session on the device). Managers don't see owners' sessions and see only their branches' devices.
- Idempotency, business config and app version (T07c): signed-in POSTs under `/api/v1` need an `Idempotency-Key`; the first response is kept 24 hours per business, user and key and replayed (`Idempotent-Replayed: true`); the same key with a different body or path is 409; a key in progress is 409; failed or rolled-back requests keep no key; `/api/v1/auth/*` and responses that set cookies are never stored (no tokens in the database); hourly purge. `GET /business/config` (X-01: business basics, branding with defaults, platform-wide maintenance from `MAINTENANCE_MODE`; nothing secret) and `GET /app/version` (X-02, global `AppVersion`). Fixed: inviting without `rights` crashed instead of defaulting to off.
- Uploads (T08, ADR-0004): `core.Upload` (keys always `{business_id}/uploads/{id}.{ext}`); `POST /uploads` returns a 5-minute upload URL for a JPEG, PNG or WebP up to 5 MB; `POST /uploads/{id}/complete` confirms the stored file matches the declared size and type. Storage adapters: Cloudflare R2 (presigned PUT, HEAD) and a local signed Django endpoint for development; production refuses anything but R2 with all `STORAGE_*` values set.
- Frontend scaffold (T09a): one Vite + React + TypeScript (strict) app with lazy route areas `/staff`, `/console`, `/rider`, `/o/:token` and `/` (placeholders for now); design tokens as CSS variables driving the Tailwind theme; self-hosted Inter and Plus Jakarta Sans; i18n with English and empty Swahili files; ESLint rules against hard-coded user-facing text, raw colours and ad-hoc number formatting; Vitest with jsdom; the dev proxy keeps the business host; the typed API client generated from `backend/openapi.yaml`; a per-area first-load budget (200 KB gzipped; 109 KB today).
- Formatting and i18n (T09b): `src/lib/format.ts`, the only place money, weights, dates, times and phone numbers are formatted. Money is rounded half-up to whole shillings on the decimal string itself, never as a floating-point number (`KSh 1,250`). Weights show one decimal (`6.4 kg`). Dates and times use the business's timezone (`Thu 2 Oct`, the year only when it isn't this year, `10am–12pm`, `5 min ago`). Phones show as `0712 345 678` or masked as `0712 ••• 678`, and other people's names as `Wanjiru K.`. Tests cover each format, Swahili falling back to English, and Swahili keys that have no English match.
- API client and shared states (T09c): the typed client (`src/api/client.ts`) adds the in-memory access token, `Accept-Language` and an `Idempotency-Key`. On a 401 it refreshes the session once, however many requests failed together, and retries with the same body and key. When the session has ended it goes to the area's log-in page with a same-site `returnTo`. Being offline, throttled or a server fault never signs anyone out. `ApiError` is built from the error envelope (fields, request ID, `retry_after`). Each user action keeps one idempotency key until it succeeds (`useActionKey`). Server field errors go onto react-hook-form fields, focusing the first. TanStack Query retries only network failures, and never retries mutations on its own. Online state combines the browser's flag with failed requests. New components: Button, Banner, Skeleton, EmptyState, and the shared states FirstLoad (200 ms delay), RefreshBar, ServerErrorBanner (Retry plus a short reference), OfflineBanner and Throttled (countdown).
